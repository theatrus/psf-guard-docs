MCP for Agents

A running PSF Guard server is also a Model Context Protocol (MCP) server at /api/mcp, on the same port as the UI. An agent such as Claude Code or Codex can read catalogs, grades and quality evidence, look into stacks, calibration and flats, read and change plans, grade frames, start imports, quality scans, stacks and WBPP runs, and back up the server. It meets the same login and permission checks as a person.

Connect an agent

On a server with user accounts, open Settings → Users → API tokens and click Connect an agent. Tick Let it grade and start jobs if the agent should write; otherwise its token only reads. Click Create token. PSF Guard makes a token of your own and shows what to paste into Claude Code and into Codex, with this server's URL. Copy the token then: it is shown once.

+ New token does the same with a Label, an expiry or another user of your choosing, and Read only, whatever the user's role for a token that only reads.

The CLI makes tokens too and prints each once. Restart the server after a CLI change:

psf-guard users token create editor --label "claude on laptop" --expires-days 90
psf-guard users token list
psf-guard users token revoke <id>

A token acts as its user and never gets more than that user has. A viewer's token reads; an editor's token can also grade and start jobs, unless it was made read only. An editor sees every token and can make one for another user. A token cannot mint or revoke tokens, so a leaked token cannot renew itself. Revoking a token stops it at once, and removing a user removes that user's tokens. See Server Accounts.

A loopback server with no accounts, such as the desktop app or psf-guard server on your own machine, needs no token. Its Settings → Agents tab shows the setup to paste. A network server with no accounts answers 401 here as everywhere else; see Server Accounts.

The desktop app picks a new port each time it starts unless you fix one. Agents links to Settings → Server, where Fixed port keeps the agent's URL across restarts; see Installation. A CLI server takes --port or port in its TOML file.

Client setup

Any client that speaks MCP's streamable HTTP transport works: give it the URL and the token as a bearer header. For Claude Code:

claude mcp add --transport http psf-guard https://guard.example/api/mcp \
  --header "Authorization: Bearer psfg_…"

For Codex, add the server to ~/.codex/config.toml and pass the token in an environment variable, so it never sits in the file:

[mcp_servers.psf-guard]
url = "https://guard.example/api/mcp"
bearer_token_env_var = "PSF_GUARD_TOKEN"
export PSF_GUARD_TOKEN=psfg_…

On the desktop app or a local server with no accounts, drop the token:

claude mcp add --transport http psf-guard http://127.0.0.1:3000/api/mcp

The URL must end in /api/mcp. The bare address serves the app and answers a POST with 405 and a note that gives the endpoint. The endpoint is stateless and answers in plain JSON, so a reverse proxy needs nothing extra and there is no session to expire. Revoke the token to cut an agent off; it stops at its next call.

What an agent may do

Every tool sends its request through the same /api routes the UI uses, as the caller. The read-only role, --allow-database-management and each route's own checks limit an agent exactly as they limit a person: each write needs the same role and database management as its button in the app. A refused call comes back as a tool error with the API's message, not a protocol failure, so the agent can explain it. Where the server sets allow_read_only_compute, a viewer's token can also build stacks, plate-solve and predict satellites, as a viewer can in the UI.

The server also gives the agent PSF Guard's ground rules: sequence analysis and quality context suggest, and nothing changes until grade_images runs; catalog predictions and header values are not pixel evidence, and a conclusion should say which it rests on.

Tools

New in 0.12. Tools for flat groups, calibration frames, duplicate repair and backups. get_jobs lists every background job, and explain_calibration can keep only the flats.

Catalog tools take a database: the ID or name list_databases reports. Planning tools take a plan_id from list_plans or a rig from list_rigs. Results are the JSON the UI itself reads. When no tool fits, api_routes lists every route api_get can read.

Jobs return at once. The agent polls get_jobs for one database's jobs, get_activity for stack builds, WBPP runs and backups across databases, or list_stacks for a stack.

Change a plan

An agent changes a plan as the app does. It reads the plan (get_plan) or its framing (get_framing), changes the object, and saves it whole with save_plan or save_framing. A save made since it read refuses, so it reads again and redoes the change. Saving changes nothing on a rig. To put a plan on the rigs, preview_activation shows what each rig's Target Scheduler database would get; apply_activation writes it only if nothing changed since that preview. See Exposures & Activation.

Look into a stack

Ask where a pattern in a stack comes from. get_stack_image with stretch: "background" shows it, and a crop shows it at full detail. get_stack_calibration shows whether a session had no flat, or a dark master built from two frames, and the temperatures those frames were shot at; get_stack provides each light's temperature for comparison. explain_calibration explains why a light cannot be calibrated: flats marked for later lights, flats at another rotator angle, darks of another exposure, or darks shot warmer than the light. get_stack also shows, per night, whether the frames were dithered: frames that walk one way without dithers turn anything fixed to the sensor into streaks. See Calibration Libraries.

Flats and their changes

Ask why some lights got last month's flats. explain_calibration with kinds: ["flat"] lists the family, the change the light sits beside and the side its flats came from. get_flat_groups shows the rig's groups and why each split: dust, light pattern or vignetting against the limits, with the dust counted by kind (new, gone, moved) and shape (compact, disk, donut, patch) and the deepest three named. Dust that moved only as far as focus travel explains is counted apart and does not split groups. get_calibration_frame shows one flat's own dust beside its session's.

Changing flat assignments manually requires write access and database management, as in the app. set_flat_group_override splits or joins groups by the sessions' response_key; set_light_flat_choice puts lights on a side of a change by its key, which get_light_flat_options lists for a set of lights. Use anyway on a suspect frame (set_calibration_frame_choice) needs write access only.

A duplicate repair needs a check first. check_calibration_duplicates starts it; get_calibration_duplicates shows the plan and its token; repair_calibration_duplicates takes that token, merges the rows, and has the masters built from them built again. No file is moved or deleted. See Calibration Libraries.

Backups

get_backups, start_backup and cancel_backup need write access and database management, as Settings › Backups does. An agent never handles secrets: start_backup refuses them whoever signs in, and writes only to the download area or the folder the schedule already uses, never a folder of the agent's choosing. It copies the server's settings and stores (meta) unless the agent asks for full, which adds every catalog. Archives are listed without download paths, and api_get reads no backups route, so an agent never hands an archive out. A person downloads an archive, or makes one with secrets, in Settings. No tool restores.

Try it without a client

TOKEN=psfg_…
curl -s https://guard.example/api/mcp \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/call",
       "params":{"name":"list_databases","arguments":{}}}'

Notes for operators

  • The endpoint sits inside the API router, so the login, the read-only role and the database-management gate apply as they do to the UI.
  • Tokens live in auth.json beside the registry as SHA-256 hashes. Tokens made in Settings work at once; a CLI change needs a restart.
  • The same token works for the REST API. See Configuration & API.
